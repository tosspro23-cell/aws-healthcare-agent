# Independent review findings

Per the challenge brief's own process checklist ("get a second,
independent AI session, not the one that wrote the code, to critically
review the phase before moving on") -- a step every phase in
[`AWS_ROADMAP.md`](AWS_ROADMAP.md) had listed but none had actually done
until now. An independent model reviewed this repository's code (commit
`36a48a8`), with explicit instructions to verify claims against the
implementation rather than take the documentation's self-assessment at
face value.

This file is the full findings list with disposition. Every "Fixed"
finding was independently reproduced against this repo's own code (or,
for the harness-measurement findings, against direct API/tool behavior)
*before* being fixed, and re-verified afterward -- against real deployed
AWS resources wherever the finding was about deployed behavior, not just
against moto/unit tests. See the exact reproduction and verification
steps in [`DECISIONS.md`](DECISIONS.md), which has the full ADR-style
reasoning for each. This file is the tracker.

Severity labels are the reviewer's own.

## Fixed

| # | Severity | Finding | Fix | Live-verified? |
|---|---|---|---|---|
| 1 | High | Any authenticated caller could read or cancel any other caller's run by `run_id` alone -- no ownership check existed anywhere. | `auth_context.py` + `owner_sub` on every record, enforced atomically in `get_run.py`/`cancel_run.py`. | Yes -- a fabricated second caller gets 404 against a real deployed run they don't own, on both the sync and Step Functions async paths; the real owner still gets 200. |
| 2 | High | `/ask`, `/runs`, and `/jobs` share one `run_id` keyspace with almost no conditional writes -- cross-path overwrites, SQS redelivery reopening completed jobs, cancellation silently undone. | Conditional `attribute_not_exists` on every record's creation; `process_job.py`'s writes conditioned on current status; `cancel_run.py` only attempts `stop_execution` for `execution_type == "STEP_FUNCTIONS"`. | Yes -- a cancelled SQS job stays cancelled after the consumer would have processed it, on the real deployed queue. |
| 3 | High | `enqueue_job.py`'s DynamoDB write and SQS `send_message` are non-atomic -- a failed send after a successful write leaves a `QUEUED` record orphaned forever, with no reconciliation path. | A `send_message` failure now gets a compensating write (`FAILED`, with the real error message) instead of silently orphaning the record. **Not fully closed**: a Lambda crash *between* the two calls (as opposed to a `send_message` call that raises synchronously) is still unhandled -- that needs a real outbox/reconciliation pattern, not a try/except, and wasn't built. | Tested via moto (a forced `send_message` exception); not separately live-tested (the failure mode is a synchronous-call exception, which behaves identically whether mocked or real). |
| 4 | High | Six constructed narrator outputs passed `safety.run_safety_checks` as `safe=True` despite being ungrounded, mis-attributed, or containing dosing/diagnosis language in unmatched phrasings; an empty answer also passed trivially. | `GroundedFact` gained a `unit` field (populated from the source biomarker, not parsed from free text) for value+unit pair verification; the ordinal-list exemption is now position-based, not value-based; the number-extraction regex bug is fixed; diagnosis/dosing pattern lists expanded; added a non-empty check. | Verified against the real pipeline (`HealthAgent.ask()`'s actual grounded facts) -- all six original probes now correctly fail. Not separately re-tested against a live Bedrock call (the fix is in the deterministic verifier, which runs identically regardless of which narrator produced the text). |
| 5 | Medium | `reasoning.py`'s pacing/nutrition branches asserted *both* trigger conditions were reported when the branch only requires *either* one; generic medication/allergy caution categories got converted into specific claims (e.g. levothyroxine, shellfish) regardless of whether that specific medication/allergy was actually what triggered the caution. | Claims are now built from only the signal(s) that actually triggered. The medication/allergy caution now requires the *specific* name (checked against the caution's own `detail` text or the structured profile) to appear before making that specific claim -- a future unrelated caution now correctly produces no claim (silence) rather than a wrong one. | N/A -- pure kernel logic, no deployed behavior to verify beyond the unit tests (which reproduce the exact scenarios: a questionnaire reporting only one signal, and an unrelated-medication caution). |
| 6 | High (for the comparison deliverable) | `stress_test.py --no-retry` didn't actually disable SDK retries (`max_attempts: 1` resolves to `total_max_attempts: 2`, confirmed directly against `client.meta.config`). | Fixed to `total_max_attempts=1`. | Re-measured live: 10/15 (matches the originally published number by coincidence -- the conclusion doesn't change, but the number is now measured correctly). |
| 7 | High (for the comparison deliverable) | `burst-async`'s success check used the raw Step Functions execution status, which reports `SUCCEEDED` even when `RecordFailure`/`RecordTimeout` gracefully caught a real agent failure (both are plain `End: true` states, not an execution-level error) -- a different, laxer success definition than `burst-queue`, which already checked the DynamoDB application-level status. The adversarial sweep also counted HTTP 200 alone, not `safe=True`. | `burst-async` (`_start_and_poll_execution`) now checks the DynamoDB record's status, matching `burst-queue`. `burst-sync`/`adversarial` (`_invoke_ask_handler`) now require `safe=True` in addition to HTTP 200. **Not done**: `race`'s consistency check and the overall reporting still don't split out transport/workflow/application/safety-level outcomes as separate dimensions -- this fix unifies the "did it succeed" question, not the full reporting granularity the finding also suggested. | Re-run live (`burst-async -n 5`): 5/5, DynamoDB-sourced `narrator_backend`/`safe` fields now populate correctly in the harness's own output. |
| 8 | Medium (documentation accuracy) | `STRESS_TEST.md` described SQS buffering as providing "guaranteed eventual success at unlimited scale," overstating what finite retries/retention/DLQ/shared-capacity actually provide. | Reworded to describe what was measured (100/100 at the largest tested burst) rather than an unconditional guarantee. | N/A -- documentation-only. |
| 9 | Medium | The "3 retry attempts" description of the Step Functions retry policy didn't account for CDK's own default retry policy (6 attempts) sitting ahead of the custom one in the ASL for a different, overlapping set of error codes. | Docstrings and docs corrected to describe both policies and how Step Functions resolves the overlap (first matching `ErrorEquals` entry wins); added a test asserting `Lambda.TooManyRequestsException` -- the only error type this project has actually observed -- appears in exactly one of the two policies. | Confirmed via the real synthesized ASL (not assumed); the previously-published throttling numbers are unaffected. |
| 10 | Medium | `narrator_backend` stayed as the *originally selected* backend even after a safety-check fallback to the mock narrator (e.g. still read `"bedrock"` when the mock's output was actually returned); the Step Functions path dropped `narrator_backend` entirely before `record_result.py` could ever persist it (a `ResultSelector` only extracted `answer`/`safe`). | `agent.py` now corrects `trace.narrator_backend` to `"mock"` on fallback. `orchestration_stack.py`'s `ResultSelector` and `RecordSuccess`'s payload now carry `narrator_backend` through; `record_result.py` persists it. | Yes -- re-deployed and re-ran a live async execution: the DynamoDB record now correctly shows `narrator_backend: "bedrock"` (previously would have shown nothing, since the field never reached this Lambda at all). |
| 11 | Medium | `AskHandler`'s IAM grants (`grant_read_write_data`, `grant_read_write` on S3) exceeded what `adapter.py` actually does (only ever writes, never reads a run record or evidence object back). The wildcard-resource test only rejected a bare `Resource: "*"`, missing a wildcard hidden inside a `Resource` list or an action-level wildcard (`"Action": "s3:*"`). | Narrowed to `grant_write_data`/`grant_put`. The shared `iam_assertions.py` helper (used by all three stack test files) now checks every element of a `Resource`/`Action` list, and flags action-level wildcards too -- while still correctly *not* flagging a legitimate bucket-object-suffix wildcard (`bucket-name/*`) or the AWS-managed `AWSLambdaBasicExecutionRole` (a managed policy, not a policy this project's own code creates). | Yes -- a real `/ask` call still succeeds end-to-end (200) after the grants were narrowed, confirming the handler never actually needed the broader permissions. |
| 12 | Medium | The ADR justifying ID-token-over-access-token rested on an incorrect premise: API Gateway's JWT authorizer does support validating against `client_id` when `aud` is absent -- exactly an access token's shape -- so access tokens were never actually incompatible with this project's authorizer config. | `get_dev_token.py` now exports the access token (`CARE_AGENT_ACCESS_TOKEN`). **No CDK/authorizer change was needed** -- the existing `jwt_audience` config already supports both token shapes. **Not done**: real per-route OAuth scopes (a Cognito custom resource server, `authorizationScopes` on each route) -- today any authenticated caller, regardless of token type, can call any route; ownership is enforced at the data layer (finding #1's fix), not via scopes. | **Not yet** -- the actual login flow needs a human at a real browser (the established pattern for this whole project's Cognito flow); whoever next runs `get_dev_token.py` should confirm the resulting access token is accepted end-to-end. |
| 13 | Medium | `start_run.py`/`adapter.py`/`enqueue_job.py` had no validation on `run_id`'s character set or length (only relevant to Step Functions execution names, but all three paths share the same `run_id` keyspace); `ExecutionAlreadyExists` was always treated as a harmless retry regardless of whether the request's input actually matched, and always reported "RUNNING" even for an already-finished execution. | New `run_id_validation.py` (Step Functions' own execution-name character/length rules), applied consistently across all three creation points. `start_run.py` now compares the existing execution's real input against the new request's, reporting a 409 conflict for a genuine mismatch and the execution's *real* current status either way. | Yes -- an invalid `run_id` (embedded space) against the real deployed `AskHandler` returns a clean 400. |
| 14 | Medium | `test_live_endpoint_smoke.py` asserted the deployed backend was `mock` and matched a local run byte-for-byte -- true before Phase 4, stale ever since the deployed default became Bedrock. The retry-policy test only checked the custom policy's presence, not that it actually governs (see finding #9). The stack-dependency test built its own stacks and called `add_stack_dependency` itself, so it couldn't have caught that call being accidentally removed from `app.py`. | Rewrote the smoke test to assert what's actually true of the current deployed system (safe, grounded, backend-agnostic) instead of exact-match text. Added a precedence-specific retry test. Refactored `app.py` into an importable `build_app()` so a test can exercise its *real* stack-wiring code, including the dependency calls, instead of a parallel reconstruction. | N/A for the two test-only fixes; `build_app()`'s refactor was confirmed not to change `cdk synth`'s output. |
| 15 | Low | The real AWS account ID was committed as a hardcoded literal in `auth_stack.py`'s default Cognito domain prefix. | Replaced with `self.account` (a CDK token resolved to the real deploying account at synth/deploy time) -- confirmed via synthesized CloudFormation to resolve to the identical value for a real deploy, so this is a source-code portability/disclosure fix with no behavior change to the live resource. | Yes -- `cdk deploy` for `CareAgentAuthStack` reported "no changes," confirming the resolved domain prefix is unchanged for this account. |

## What the review said to keep as-is

Quoted from the review, not re-verified independently here but consistent
with what this project already believed about its own design: the
reasoning/narration separation and optional deterministic path; the
five-stack decomposition (the coupling problem was shared mutable state,
now fixed, not stack count); BM25 and read-only parameterized SQLite
access; the S3/SQS storage baseline (encryption, public-access blocking,
TLS enforcement); conditional terminal writes in the Step Functions path
(`record_result.py`) as the pattern worth extending everywhere, which
finding #2's fix now does across all three paths; and the
experiment-driven approach to finding real throttling/concurrency
behavior in general.
